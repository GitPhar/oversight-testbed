# Audit of ng-p3-17: is P3-5c's blur-type term still needed when readout error may be up to 3x each job's calibration value?

## In plain English

The verdict stands: **untestable**, and the bet is not scored. You reach that verdict either way. Under the pre-registration's own words, the second run stopped before h268's bootstrap finished (§5.3), and §3 says the run is never repeated. D46 had already used up the one re-run. Under D48, the re-run failed D48's own exact-reproduction check on h088. I found what the record did not: why h088 did not reproduce. The code rebuilds each pair's reference state with the Aer simulator on every run. On h088 and h268 that state differs between two calls by about 3e-16, while on h221 it is identical. The fits carry that difference into the fourth decimal of logL. So D48's check was close to impossible to pass on h088, and its premise that "h268's numbers are fixed by the seed" was false. Two plain-English sentences contradict the results file's own table: the wide-bounds sentence and the "2 to 20 times" ratio. One sentence names the wrong mechanism for the null shift. The Novelty line states the unscored re-run as "ours says". The ledger row does not yet carry the novelty fields. The scored verdict is not affected by any of these; five sentences must be rewritten. The cheapest next test is P3-19 (the 5 November job, $0) with the reference state computed once and committed before data. It should also add a correlated-readout rival, because this bet excludes only per-qubit, fixed-over-the-job readout knobs.

## The case that this result is false

*Written before the checklist, as assigned.* The headline says "untestable", but the strongest reading of the record says the bet passed. The reason for the untestable verdict is not a fact about the chip, the data or the statistic. It is a 1.4e-4 difference in a log-likelihood of about −46,302. That difference changed no label, no p, no B, and no comparison that matters. Every LR in the re-run sits at least 2.3 times above its null's 99th percentile and above the largest of 2,000 null draws. D48's check existed to show that h268 could not be "re-rolled". A seed-fixed pipeline whose observed fits wobble in the fourth decimal cannot be steered toward a pass by anyone, so the check's purpose was met even though its letter was not. On this view, untestable trades a real, pre-registered answer for procedural purity. It also keeps a pass at engine odds 0.55, against Sean's 0.30, out of the Brier score. That cuts against the engine, but it still distorts the record of what the archive says.

The opposite case is just as strong, and it says the bet was never testable as written. Under §5.3 the bootstrap on h268 "did not complete" in run 2, and §3 says "The run is never repeated." D46 had already used the one re-run that §7 allows. D48 then re-read §5.3 after seeing h221 and h088 both "still needed", in the one direction that let the run continue. Had the check passed, a pre-registered untestable would have turned into a scored pass by a rule reading written after two-thirds of the data were known. So either way, a scored pass would rest on a decision made after data. The checklist below decides between the two cases.

## What would break it next

The verdict is a process fact, and nothing re-run on this archive can change it, because the run is closed. The question the bet asked remains open. The cheapest test that could overturn the re-run's unscored reading:

1. **P3-19 as already mapped** (bounded readout knobs on the 5 November job; $0, laptop about 2 to 6 h). Two changes come from this audit:
   - (a) Compute each pair's ρ_ref once before the run, commit it with its hash in `USES`, and have `run()` load it rather than rebuild it. Otherwise first show bit-reproducibility (for example Aer `max_parallel_threads=1`, three calls, identical hashes) in the design review.
   - (b) Write any reproduction tolerance for a re-run into the pre-registration, before data, not into a deviation row after a stall.
2. **A correlated-readout rival on this archive**, reported as exploratory because the bet is closed. Add the three extra assignment parameters of a 4×4 correlated readout to cohR, bounded at 3× the off-diagonal calibration terms. This bet excludes only per-qubit readout knobs that are fixed over the job. The full model's preference for knobs at their lower bound (8 of 12) is the SPAM gauge at work (Lin 2021; Jayakumar 2024): the fit trades calibrated misreading for blur. A correlated knob is the rival most likely to absorb h268's LR of 34.5. Cost $0, about 1 laptop hour for point fits, about 3 h with the two-generator bootstrap.

*Recommended lesson for the ledger:* "same seed, same numbers" (D46, D48) was asserted twice and never tested. A design review should run the pipeline twice on synthetic counts and compare hashes before any re-run rule relies on determinism.
