# Design review of ng-p3-15

## In plain English

As built, this test can answer its main question: did the barrier make 3 November's chip say "yes" half the time? It has the shots to see an effect the size of 3 November's gap many times over, and it would correctly come back negative if the barrier does nothing. That holds even if IBM's servers ignore the barrier, because a barrier the server ignores could not have caused 3 November either. But the answers written in advance (§5) would be wrong in two plausible worlds. If grouping the shots into one block is what matters, the pre-written sentence says the cause was "something this test held fixed", when the test varied it. If the chip is back in its 3 November state on every arm, the sentence says the barrier "did not bring back 3 November's result", when the result came back. The design also claims its one-block arm matches 3 November's set-up, but that arm shares a job with 31 other circuits, and nothing offline can say whether its 1,000 shots run back to back. One prediction it needs is missing. The code would score a short-shot job instead of calling it untestable. The planned 6.8 QPU s is nearly three times what Sean approved. All six are fixable before data without changing what is tested, so the verdict is **fix first**.

### D2. Every manipulation takes effect: **flaw** (F3; grouping-in-time is cannot-check, F4)

Compiled circuits (`dry1.py`). Nothing re-transpiles them: `submit()` and `run_hardware` pass them to SamplerV2 as is.

| arm | ops | active qubits | barrier |
|---|---|---|---|
| NB / NI | sx 219, rz 153, cz 117, x 5, measure 9 | 117, 123, 124, 125, 136, 141, 142, 143, 144 | none |
| BB / BI | same + barrier 1 | same | at index 494 of 504, on all 9 qubits, immediately before the first measure |
| R0 | measure 9 | same, clbit map 117→0, 125→1, 124→2, 123→3, 144→4, 136→5, 143→6, 141→7, 142→8 (= the ISA map) | none |

This matches 3 November's circuit: the archive's op counts list `barrier: 1` while its gate list omits it, and `measure_all()` (encoder.py:162) places it exactly there. The QPY round trip preserves every circuit (`==`), barrier included. QPY bytes differ between two dumps of the same circuits. That does not matter for `submit()`, which hashes the saved file, but an auditor must compare circuits by equality, not by hash.

Job structure (32 PUBs, 5,000 shots, as pre-registered):
- run 1, unit order [BB, NB, interleaved]: `BB×1000 NB×1000 R1 NI BI NI R0 NI BI BI BI R0 BI NI NI R0 NI BI NI R1 NI R0 BI R0 R1 BI NI NI R1 BI R1 BI` (pieces ×100)
- run 2, unit order [interleaved, BB, NB]: 30 pieces, then `BB×1000 NB×1000`

Per-PUB shots survive the real client path. A local-mode `Batch(FakeFez)` + `SamplerV2.run(pubs, shots=100)`, with the QPY-loaded circuits, returned exactly [1000, 1000, 100 × 30] (`dry2.py`).

**Barrier, simulated** (`dry3.py`, the `predict()` construction, 100,000 shots, seed `sim`):

| schedule | FakeFez P(yes) | 3 Nov snapshot P(yes) |
|---|---|---|
| barrier, ALAP | 0.2651 | 0.2654 |
| no barrier, ALAP | 0.2651 | 0.2654 |
| no barrier, ASAP | 0.2645 | 0.2655 |
| **barrier, ASAP (not in the pre-registration)** | **0.2754** | **0.2742** |

Under ALAP the barrier changes nothing, even in simulation. Under ASAP, the barrier is what differs between the arms: barrier-ASAP minus no-barrier-ASAP is **+0.011** (SE 0.002). The barrier then makes qubits 117, 125, 124, 123, 144, 136 and 143 idle about 4.8, 4.4, 3.8, 2.6, 1.6, 0.6 and 0.2 µs in their final states before measurement. The pre-registration's three predictions pair barrier-ALAP with no-barrier-ASAP (+0.0006). That pairing misstates what the barrier could do on an ASAP server, and the measure-time printout hides it: barrier-ASAP measures every qubit at 8.052 µs, like ALAP, but its gates run early. The direction holds, and is 9× below the Δ ≥ 0.10 bar, which is consistent with the 7% odds.

**Grouping.** The manipulation changes the PUB layout as claimed. Whether BB's 1,000 shots execute consecutively on the server, or round-robin with the other PUBs, **cannot be checked offline**. The local result carries no execution spans. What would settle it after the job, for free: `job.result().metadata["execution"]["execution_spans"]`, plus per-shot bitstrings. The code saves neither (it keeps only `get_counts()`).

### D3. Every control can fail: **holds**

- **NI vs 4 November's 0.246** (band ±0.05). It rejects a chip back in its 3 November state (W5: NI 0.50, `within_0.05: false`). Under no drift, the chance of a false failure is P(|Z| > 0.05/0.0166) ≈ 0.003. The 0.246 is reproduced exactly from `data/p3-2-3-raw.json` (arm A, 2,000 shots) with the same `p3sim.p_yes`. Instance spread there was 0.035 per 100-shot piece against a binomial 0.043, so binomial SEs are not optimistic. **Limitation, not a flaw:** the band (0.196–0.296) also contains the noiseless ideal (0.294) and the simulator (0.265), so "control passed" means only "P(yes) has not moved by more than 0.05". The per-qubit marginals are the finer check.
- **R0/R1** gate nothing. They are reported readout matrices, and on 4 November they caught qubit 141's 21% readout error.
- The 3 November 0.502 reproduces exactly from `entangled-mind/results/stage1-run-1.json` with the same function.
- There is no on-chip check that the barrier changes execution (see the pre-mortem, point (a) below, and optional O1).

### D4. Rivals are matched: **holds**

There are no competing fitted models. The three explanations are tested by contrasts of equal size: barrier pooled 2,000 v 2,000 shots, grouping pooled 2,000 v 2,000, day via NI and run 2. Neither rival is built to lose. The scored rule credits only the barrier, which is the bet's choice. The gap is in the sentences (F1), not in the design.

### D5. A dumb baseline is beaten, and the design can see the effect: **holds**

- Dumb predictor ("the chip equals its simulator", BB ≈ NB ≈ 0.265): P(pass) ≈ 0, since 0.40 is about 10 SE above 0.265 (W3).
- Power at 3 November's effect size (BB 0.50, NB 0.25): SE(Δ) ≈ 0.021, so z ≈ 12 and P(pass) ≈ 1. At half that size (BB 0.42, NB 0.30): P(pass) ≈ 0.92 × 0.83 ≈ 0.76. At the simulator's ASAP barrier effect (+0.011): P(pass) ≈ 0.
- "No effect" readings: the margin is 0.05. SE of the pooled barrier contrast is 0.0137 at p ≈ 0.25, and 0.0153 at p ≈ 0.375. The 90% CI half-width is 0.023 to 0.025. P(declare equivalence | true 0) ≈ 0.955 (0.90 at p ≈ 0.375). The two-sided 5% MDE at 80% power is ≈ 0.038, below the margin. Drift contrasts are the same size.
- **QPU budget.** The formula is 0.28 ms/shot + 2 s. Against the three billed jobs: 1 PUB × 1,000 → 2.28 estimated v 2.0 billed; 39 × ~4,000 → 45.7 v 44.0; 200 × 100 → 7.6 v 8.0. So 32 PUBs × 5,000 shots → 3.4 s estimated, with about 3 to 4 s likely billed per run and 6 to 8 s for both. That is inside the 5 s per-run cap, the 10 s ledger budget and the reserve rule (54 s used of 420 s). It is about 3× Sean's approval (F6).

### The author's two flagged points

**(a) If the server ignores the barrier.** The design still separates the three factors. If the server measures as late as possible, BB v NB is null by construction (W3), and the bet fails. The fail is still a correct answer to the question asked. A barrier the server ignores today could not have caused 3 November, provided the server treated that day's identical submission the same way. The fail sentence should state that assumption. Grouping and day are still estimated (pooled grouping contrast; NI v 0.246; run 2). So the test is **not** untestable by its own rule, and §5 rightly does not call it untestable. But §5 cannot say *why* the barrier did nothing, and §6 says so honestly. One caution: "what the barrier could change if IBM schedules ASAP" is mis-computed (F3). The right number is about +0.01, which is the strongest offline reason to expect this fail. A cheap on-chip probe (O1) would turn the pre-mortem from an untestable guess into a measured fact.

**(b) `overwrite_calibration`.** No P3-15 path calls it. `predict()` uses `NoiseModel.from_backend` of the live target through `p3sim.simulator(be)` with `zz_phase=0`. The only callers are `p3_1_scheduled.py` and `p3_5_fits.py`. **The D8 fix holds** (`dry4.py`):
- It assigns the whole `qubit_properties` list and asserts it. Qubit 123: FakeFez T1 155.4 µs → snapshot 100.8 µs, written to both the target and `backend.qubit_properties`, with the original FakeFez untouched (deep copy).
- The noise model really uses it. X, then a 20 µs delay, then measure on q123 with T1 = T2 = 5 µs gives P(1) = 0.029, against 0.879 on FakeFez and 0.876 with `legacy_t1t2_bug=True`, which reproduces the old no-op.
- Readout, sx/x and CZ errors are written, CZ in both directions. All 8 CZ pairs the circuit uses are in the snapshot.
- ZZ is composed into the local CZ errors. P(yes) is 0.268 at 0 rad, 0.337 at 0.1 rad and 0.642 at 1.0 rad; qubit 125's P(1) is 0.695, 0.586 and 0.289. With `legacy_zz_bug=True`, it stays 0.268 at both. The `!= old` assert is meaningful: `QuantumError` defines `__eq__`, and equal errors compare equal.
